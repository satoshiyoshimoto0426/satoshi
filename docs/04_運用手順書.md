## 0. このシステムを一言で

毎日 4 回(06:00 / 12:00 / 18:00 / 23:00 JST)公的サイトを巡回し、毎朝 07:00 に AI が日次まとめを作り、
07:30 に 2 つの LINE 公式アカウントへ配信する。**新着が 0 件の日も「本日の新着はありません」を配信する。**

> **運用ルール(全員に周知)**
> 朝 8 時までに LINE が届かない日は、新着が無かったのではなく **システム障害** です。
> 管理者へ連絡してください。

## 1. 日常運用

### 1.1 毎朝の確認(2 分)
1. LINE 2 アカウントに配信が届いているか。
2. Slack の通知チャンネルに 🔴(error)が出ていないか。
3. 🟡(warn)が出ていたら §3.2 のソース故障対応へ。

### 1.2 週次の確認(10 分)
`05_品質監査チェックリスト.md` に従い、各チャネル 5 件を抜き取り監査する。

## 2. コマンド

すべて `pnpm cli <サブコマンド>`(本番コンテナでは `node dist/cli.js <サブコマンド>`)。

| コマンド | 用途 |
|---|---|
| `pnpm cli collect` | 巡回を手動実行 |
| `pnpm cli collect --source <id>` | 特定ソースだけ巡回(故障調査用) |
| `pnpm cli collect --bootstrap` | 初回登録時。既存記事を「既知」にして翌朝の配信に流さない |
| `pnpm cli summarize --date 2026-09-12` | 指定日のまとめを生成 |
| `pnpm cli summarize --date 2026-09-12 --force` | 既存のまとめを作り直す |
| `pnpm cli preview --date 2026-09-12` | 配信予定の文面を標準出力で確認 |
| `pnpm cli deliver --date 2026-09-12` | 配信(冪等。送信済みなら何もしない) |
| `pnpm cli deliver --date 2026-09-12 --dry-run` | 送信せず文面だけ確認 |
| `pnpm cli approve --date 2026-09-12 --channel welfare` | 承認モード時に配信を承認 |
| `pnpm cli validate-config` | 設定 YAML の検証 |
| `pnpm cli verify-sources` | 全ソース URL の到達確認とセレクタ検証 |
| `pnpm cli verify-sources --fix` | 失敗したソースを自動で `enabled: false` にする(NG が半数超なら中止) |
| `pnpm cli health` | 異常なソースの一覧(連続失敗 / 候補 0 件) |
| `pnpm cli test-broadcast` | 各チャネルへ疎通確認を送る(既定は未送信。実送信は `--yes`) |

### 2.1 本番(Cloud Run Jobs)での手動実行

```bash
# 巡回をいますぐ回す
gcloud run jobs execute seido-watch-collect --region asia-northeast1

# 日付を指定してまとめ直す(引数の上書き)
gcloud run jobs execute seido-watch-summarize --region asia-northeast1 \
  --args=summarize,--date,2026-09-12,--force

# 配信をやり直す
gcloud run jobs execute seido-watch-deliver --region asia-northeast1 \
  --args=deliver,--date,2026-09-12
```

## 3. 障害対応

### 3.1 朝に LINE が届かない

| 症状 | 確認 | 対応 |
|---|---|---|
| Slack に 🔴 が出ている | 通知本文のジョブ名 | 該当ジョブのログを見る(§3.4) |
| Slack に何も出ていない | Cloud Scheduler の実行履歴 | Scheduler が発火していなければ手動実行(§2.1) |
| deliver は成功しているが届かない | LINE Official Account Manager の配信履歴 | 月間メッセージ通数の上限超過を疑う(§3.3) |

復旧手順(まとめは出来ているが配信が失敗した場合):
```bash
pnpm cli preview --date <当日>       # 文面を確認
pnpm cli deliver  --date <当日>      # 再配信(冪等キーが効くので二重配信にならない)
```

まとめ自体が無い場合:
```bash
pnpm cli summarize --date <当日> --force
pnpm cli deliver   --date <当日>
```

### 3.1a Slack に「未分類アイテムが残っています」が出た

AI の分類が失敗しています(API 障害、レスポンスがスキーマに合わない等)。
**この日はそのチャネルへ配信されません。**「新着なし」と偽らないための意図的な動作です。

```bash
pnpm cli collect                      # 分類を再実行(巡回済みの未分類分が処理される)
pnpm cli summarize --date <当日> --force
pnpm cli preview   --date <当日>      # 文面を確認
pnpm cli deliver   --date <当日>
```

Anthropic API 側の障害なら復旧を待ちます。記事自体は保存されているので、
3 日以内に分類が終われば繰り越しで配信されます。

### 3.1b Slack に「候補が取れないソース(セレクタ失効の疑い)」が出た

HTTP は成功しているのに一覧からリンクが 1 件も取れない状態が 4 回続いています。
サイト改修で `itemSelector` が失効した可能性が高く、**放置するとそのソースの情報は
一切届かないまま「正常に監視した」ように見えます。** §3.2 の手順で修正してください。

### 3.2 ソースが連続失敗している(Slack に 🟡)

原因の大半は **サイト改修による URL 変更または CSS セレクタの失効** です。

```bash
pnpm cli health                       # 失敗しているソースを特定
pnpm cli verify-sources --source <id> # 到達確認とセレクタ検証
```

> **`verify-sources --fix` は NG が半数を超えると書き換えを中止します。**
> 一斉に失敗するのは個々のサイトではなく実行環境側(プロキシ・DNS・egress)の
> 障害である可能性が高く、そのまま書き換えると全ソースが無効化されて
> 「監視していないのに正常に見える」状態になるためです。
> ネットワークを確認してからやり直してください。本当に全件無効化したい場合のみ
> `--force-fix` を付けます。

- **到達しない(404/リンク切れ)** → 新しい一覧ページの URL を探し、`config/sources/*.yaml` の `url` を更新。
- **到達するが候補 0 件** → `itemSelector` が失効している。ブラウザの開発者ツールで
  新着リンクを囲む要素を調べ、`itemSelector` と `includeUrlPatterns` を更新。
- **すぐ直せない** → `pnpm cli verify-sources --fix` で一時的に `enabled: false` にし、
  課題として起票する。無効化したままにしないこと(見落としの原因になる)。

修正後は必ず:
```bash
pnpm cli validate-config
pnpm cli collect --source <id>
```

### 3.3 LINE のメッセージ通数上限

- 友だち数 20 名 × 1 通/日 × 31 日 ≒ 620 通/月・アカウント。
- 無料のコミュニケーションプラン(200 通/月)では足りないため、**ライトプラン以上が必要**(M3-10)。
- 上限に達すると配信が失敗する。LINE Official Account Manager でプランと残通数を確認する。

### 3.4 ログの見方

```bash
# 直近のジョブログ
gcloud logging read \
  'resource.type="cloud_run_job" AND resource.labels.job_name="seido-watch-deliver"' \
  --limit 50 --format json

# 特定の実行 ID で絞る
gcloud logging read 'jsonPayload.runId="<runId>"' --limit 200
```

ログは JSON Lines。主なフィールド: `job` / `runId` / `sourceId` / `channelId` / `count` / `durationMs` / `error`。
**トークン・API キー・Webhook URL は `[REDACTED]` に伏せられます。**

## 4. 設定変更

### 4.1 情報源を追加する

`config/sources/` の該当ファイルに 1 ブロック追記するだけ(FR-01 / NFR-05)。

```yaml
  - id: wf_example_new
    name: 例) ○○県 障害福祉課 事業者向けお知らせ
    type: html
    url: https://www.pref.example.lg.jp/shogai/jigyosha.html
    channels: [welfare]
    priority: medium
    region: ○○県
    enabled: true
    html:
      itemSelector: 'main a'
      includeUrlPatterns: ['/shogai/']
      excludeUrlPatterns: ['javascript:', '#', 'twitter.com', 'facebook.com']
    note: ○○県の指定基準・独自加算の変更を検知する
```

追加後:
```bash
pnpm cli validate-config
pnpm cli verify-sources --source wf_example_new
pnpm cli collect --source wf_example_new --bootstrap   # 既存記事を流さない
```

> `--bootstrap` を忘れると、そのサイトの過去記事が翌朝のまとめに大量に流れ込みます。**必ず付けること。**

### 4.2 情報源を止める

`enabled: false` にして `pnpm cli validate-config`。コード変更もデプロイも不要
(次回のジョブ実行で反映される。ただし config はイメージに同梱されるため再デプロイが必要)。

### 4.3 配信時刻を変える

`infra/terraform/main.tf` の `schedule` を変更して `terraform apply`。
併せて `config/channels.yaml` の `deliverAt` と、`summarize` のカットオフ(07:00)を見直すこと。

### 4.4 配信件数・文字数を変える

`config/channels.yaml` の `maxItems` / `minItems` / `maxChars` / `relevanceThreshold`。
- 情報が多すぎる → `relevanceThreshold` を 0.7 に上げる
- 情報が少なすぎる → 0.5 に下げる

### 4.5 承認モードにする

`config/channels.yaml` の該当チャネルを `requireApproval: true` に。
以後は `pnpm cli approve --date <日付> --channel <id>` を実行するまで配信されません。
本番投入直後の 3 日間はこのモードで運用することを推奨します(詳細設計書 §13)。

## 5. シークレットのローテーション

```bash
# 1. LINE Developers コンソールでチャネルアクセストークンを再発行
# 2. 新しい値を Secret Manager に新バージョンとして追加
#    対話式のスクリプトを使うと値が画面にもシェル履歴にも残らない。
export PROJECT_ID=<プロジェクトID>
bash scripts/set-secrets.sh

#    個別に入れたい場合(値がシェル履歴に残らないよう先頭に空白を置く)
 printf '%s' '<新しいトークン>' | \
   gcloud secrets versions add line-token-welfare --data-file=-

# 3. 次回のジョブ実行から自動的に新バージョンが使われる(latest 参照のため)
#    すぐ反映したい場合は手動実行して確認
gcloud run jobs execute seido-watch-deliver --region asia-northeast1 \
  --args=deliver,--dry-run

# 4. 旧バージョンを無効化
gcloud secrets versions disable <旧バージョン番号> --secret=line-token-welfare
```

同じ手順で `anthropic-api-key` / `slack-webhook-url` も更新できます。
**トークンの値をコミット・Slack・チケットに貼らないこと。**

## 6. デプロイ

**デプロイは自動です。** `main` ブランチへ push すると GitHub Actions が
検証 → イメージのビルド → Terraform 適用 → 疎通確認(送信なし)まで行います。

```
main へ push
  ↓
lint / typecheck / test / 設定検証
  ↓
Artifact Registry へイメージを push(タグはコミット SHA の先頭 12 桁)
  ↓
terraform apply(Cloud Run Jobs / Scheduler / Firestore / 監視)
  ↓
3 ジョブが新しいイメージを指しているか照合
  ↓
validate-config でイメージの起動と設定読み込みを確認(配信はしない)
```

pull request では `terraform plan` の差分が出るだけで、適用はされません。
手動で走らせたいときは GitHub の Actions タブから「デプロイ」を Run workflow します。

### 6.1 初回だけ必要な設定(1 回きり)

#### どこで実行するか

`infra/bootstrap.sh` と `scripts/set-secrets.sh` は **bash のスクリプト**です。
**Windows の PowerShell やコマンドプロンプトでは動きません。**

| 実行環境 | 使えるか | 備考 |
|---|---|---|
| **Google Cloud Shell(ブラウザ)** | ◎ おすすめ | インストール不要。gcloud が最初から入っていてログイン済み |
| macOS / Linux のターミナル | ○ | `gcloud` のインストールとログインが必要 |
| Windows の WSL / Git Bash | ○ | 同上 |
| Windows の PowerShell | × | bash スクリプトは実行できない |

**Google Cloud Shell がいちばん簡単です。** ブラウザだけで完結し、何もインストールしません。

#### Google Cloud Shell での手順

1. ブラウザで <https://console.cloud.google.com/> を開き、**対象のプロジェクトを選択**します。
2. 画面右上の **ターミナルのアイコン**(`>_`)をクリックします。画面下部に黒い画面が開きます。
   初回は「Cloud Shell の承認」を聞かれるので承認します。
3. 開いた画面に、次を **1 行ずつ** 貼り付けて Enter を押します。

```bash
git clone https://github.com/satoshiyoshimoto0426/satoshi.git
cd satoshi
```

4. プロジェクト ID を指定します。`<プロジェクトID>` は実際の ID に置き換えてください
   (Cloud Shell の画面上部や、Google Cloud コンソールの画面上部に表示されています)。

```bash
export PROJECT_ID=<プロジェクトID>
export GITHUB_REPO=satoshiyoshimoto0426/satoshi
```

5. 初期設定を実行します。数分かかります。

```bash
bash infra/bootstrap.sh
```

6. シークレット(トークン)を投入します。
   値を貼り付けて Enter を押します。**入力した文字は画面に表示されません**(正常です)。

```bash
bash scripts/set-secrets.sh
```

7. `bootstrap.sh` が最後に表示したリポジトリ変数を GitHub に設定します(次項)。

> Cloud Shell は 1 時間ほど操作しないと切断されます。切れたら同じ画面を開き直し、
> `cd satoshi` してから続きのコマンドを実行してください。
> 初期設定スクリプトは何度実行しても同じ結果になるので、途中で切れた場合は
> 最初からやり直して構いません。

#### PowerShell しか使えない場合

Windows に gcloud をインストールし、PowerShell から次のように WSL 経由で実行できます。

```powershell
wsl bash infra/bootstrap.sh
```

ただし WSL の準備が必要なので、**Cloud Shell を使うほうが確実です。**



下記の「どこで実行するか」を読んでから、次の 2 つを実行します。何度実行しても同じ結果になります。

```bash
export PROJECT_ID=<Google Cloud のプロジェクト ID>
export GITHUB_REPO=satoshiyoshimoto0426/satoshi

bash infra/bootstrap.sh      # API 有効化・状態バケット・権限・鍵なし認証・シークレットの箱
bash scripts/set-secrets.sh  # トークンの値を投入(画面に表示されません)
```

> **`set-secrets.sh` で入れる 4 つの値の取り方は
> [06_認証情報の取得手順.md](06_認証情報の取得手順.md) にまとめてあります。**
> LINE のチャネルアクセストークン、Anthropic の API キー、Slack の Webhook URL を
> どの画面のどこで発行するかを、順を追って書いています。

> **この順序は必須です。** Cloud Run Jobs はジョブ作成時に、参照先シークレットの
> 「値(バージョン)が存在すること」を検証します。値の投入前に push すると
> ジョブの作成で失敗します。4 つすべてに値を入れてから push してください。
>
> Slack 通知を使わない場合は、ダミー値を入れるのではなく
> `infra/terraform/main.tf` の各ジョブの `secret_env` から `SLACK_WEBHOOK_URL` を
> 外してください(ダミー値だと通知の失敗に気づけません)。

`bootstrap.sh` が最後に GitHub のリポジトリ変数 5 つを表示するので、
`Settings > Secrets and variables > Actions > Variables` に設定します。

| 変数 | 内容 |
|---|---|
| `GCP_PROJECT_ID` | プロジェクト ID |
| `GCP_REGION` | `asia-northeast1` |
| `GCP_WIF_PROVIDER` | Workload Identity プロバイダのリソース名 |
| `GCP_DEPLOY_SA` | デプロイ用サービスアカウントのメールアドレス |
| `GCP_FIRESTORE_LOCATION` | Firestore のロケーション(作成後に変更できない) |
| `TF_STATE_BUCKET` | Terraform の状態を置くバケット名 |

以降、設定は不要です。

初回デプロイが通ったら、手元で次を実行して `.terraform.lock.hcl` をコミットしてください。
プロバイダのバージョンが固定され、CI と手元で同じものが使われます。

```bash
cd infra/terraform
terraform init \
  -backend-config="bucket=${PROJECT_ID}-tfstate" \
  -backend-config="prefix=seido-watch"
git add .terraform.lock.hcl && git commit -m "chore: Terraform プロバイダのバージョンを固定"
```

### 6.2 なぜサービスアカウントキーを使わないか

キーの JSON を GitHub に置くと、漏れたときに無期限で悪用できます。
Workload Identity 連携なら、**このリポジトリの `main` ブランチからのみ**、
短命のトークンで認証されます(NFR-03)。`bootstrap.sh` はプロバイダに
`assertion.repository` と `assertion.ref` の両方の条件を付けます。

ブランチまで絞るのは、リポジトリだけの条件では **push 権限がある人が任意のブランチに
自作のワークフローを置けばデプロイ用トークンを取得できてしまう**ためです。
併せてデプロイ用サービスアカウントには「シークレットの値を読む権限」を与えていません
(IAM を設定できるだけのカスタムロールにしています)。

トークンや API キーは GitHub にも git にも入りません。
`scripts/set-secrets.sh` で Secret Manager へ直接入れ、Cloud Run Jobs が実行時に読みます。

### 6.3 ロールバック

イメージのタグはコミット SHA なので、戻したいコミットを指定して適用し直します。

```bash
cd infra/terraform
terraform init \
  -backend-config="bucket=${PROJECT_ID}-tfstate" \
  -backend-config="prefix=seido-watch"
terraform apply \
  -var="project_id=${PROJECT_ID}" \
  -var="image=asia-northeast1-docker.pkg.dev/${PROJECT_ID}/seido-watch/seido-watch:<戻したいSHA12桁>"
```

あるいは `git revert` して main へ push すれば、自動デプロイが前の状態を作り直します。

### 6.4 デプロイが失敗したとき

| 症状 | 原因と対処 |
|---|---|
| 認証で失敗する | リポジトリ変数 5 つが未設定、または `bootstrap.sh` が未実行 |
| `terraform init` で失敗する | 状態バケットが無い、またはデプロイ用 SA に権限が無い。`bootstrap.sh` を再実行する |
| イメージの push で失敗する | Artifact Registry が未作成。ワークフローは初回に先行作成するので、まず再実行を試す |
| ジョブ作成で `Secret ... not found` | `bootstrap.sh` が未実行。先に実行する |
| ジョブ作成で バージョンが無い旨のエラー | `scripts/set-secrets.sh` が未実行、または一部のシークレットが空 |
| イメージ照合で失敗する | apply が意図どおり効いていない。Actions のログで apply の出力を確認する |
| 起動確認で失敗する | 設定 YAML の不備、またはシークレット未投入 |
| `firestore` の作成で失敗する | ロケーションは作成後に変更できない。既存 DB がある場合は `firestore_location` を合わせる |

**`terraform apply` より前で失敗した場合**(検証・認証・イメージのビルドなど)は、
稼働中のジョブは前のイメージのまま動き続けます。配信は止まりません。

**`terraform apply` が成功したあとで失敗した場合**(イメージ照合・起動確認)は、
ジョブは既に新しいイメージに差し替わっています。翌朝の配信は新しいイメージで走るため、
原因を確認して直すか、§6.3 の手順で前のイメージへ戻してください。

## 8. 重要な既知の制約 ― 情報源 URL は未検証

`config/sources/*.yaml` に登録した **URL と CSS セレクタは、開発環境から官公庁サイトへ
アクセスできなかったため実地検証できていません**。本番投入前に必ず実施してください。

```bash
pnpm cli verify-sources          # 到達確認 + セレクタ検証。NG があれば終了コード 1
pnpm cli verify-sources --fix    # NG を enabled: false に自動変更
```

NG のソースは §3.2 の手順で URL とセレクタを修正してから有効化してください。
この作業を省くと「巡回しているつもりで何も取れていない」状態になり、見落としの原因になります。
