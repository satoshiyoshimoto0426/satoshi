## 1. 背景と目的

### 1.1 背景
- 以下の 2 領域は法改正・制度改正・行政通知の頻度が高く、後手に回ると事業運営上のリスク(報酬請求誤り、助成金要件の見落とし、指定基準違反等)に直結する。
  1. AI リスキリング研修に関わる制度(人材開発支援助成金、教育訓練給付、リスキリング関連施策、AI ガバナンス関連法制)
  2. 就労支援事業所(就労移行・就労継続 A/B 型・就労選択支援)および放課後等デイサービスの制度・報酬・運営基準
- 現在は担当者が手動で省庁サイトを巡回しており、属人化と見落としが発生している。

### 1.2 目的
公的な一次情報源を **自動で継続的に監視** し、AI が **日次の「まとめ」** を生成して、2 つの LINE 公式アカウントへ **毎朝自動配信** する。チームメンバーは LINE を見るだけで最新動向を把握できる状態を作る。

### 1.3 ゴール(成功の定義)
| # | ゴール | 測定方法 |
|---|---|---|
| G1 | 毎朝 07:30 JST に両アカウントへ配信される | 配信成功率 ≥ 99.5%/月 |
| G2 | 掲載される全項目に出典 URL が付く | 出典欠落 0 件(自動検証) |
| G3 | 情報量が過剰にならない | 1 配信あたり 3〜7 項目、本文 1,500 文字以内 |
| G4 | 誤情報・幻覚を配信しない | 全項目が実在 URL に紐づき、要約は原文に根拠を持つ(人手抜き取り監査で逸脱 0) |
| G5 | 見落としを減らす | 監視対象ソースの新着取得漏れ 0(取得ログで検証) |

## 2. スコープ

### 2.1 対象範囲(In Scope)
- 情報源の定期収集(RSS / HTML 差分監視 / 公式 API)
- 収集情報の重複排除・関連度判定・分類(2 チャネルへの振り分け)
- AI による日次要約の生成(出典リンク付き)
- LINE 公式アカウント 2 つへのブロードキャスト配信
- 配信前の品質ゲート(出典 URL 実在確認、文字数、禁則)
- 運用者向けの管理・監視(実行ログ、失敗通知、手動再実行)
- 情報が無い日の「新着なし」配信の可否設定

### 2.2 対象外(Out of Scope)
- 法令の逐条解釈や法的助言の提供(要約は「一次情報への案内」に限定)
- LINE 上での双方向チャットボット応答(将来拡張)
- 有料データベース(判例 DB、業界紙)の購読・取り込み
- 配信内容の人手承認ワークフロー(初期リリースでは自動配信。ただし「承認モード」を設定で切替可能に設計)

## 6. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | 情報源は YAML で宣言的に定義でき、追加・無効化・チャネル紐付け・優先度をコードを変えずに変更できる | Must |
| FR-02 | 各情報源を 1 日 4 回(06:00 / 12:00 / 18:00 / 23:00 JST)巡回し、新着・更新を検知する | Must |
| FR-03 | 新着検知は URL 正規化 + 本文ハッシュで重複排除し、同一情報の再配信を防ぐ | Must |
| FR-04 | 検知した記事について AI が「関連チャネル(複数可)/ 関連度スコア / 重要度(高・中・低)/ 種別(法改正・報酬改定・通知・パブコメ・予算・その他)」を判定する | Must |
| FR-05 | 毎朝 07:00 JST に、直近 24 時間の関連度スコア閾値以上の記事をチャネルごとに集約し、AI が日次まとめを生成する | Must |
| FR-06 | まとめは「見出し / 要点(1〜2 文)/ 影響を受ける対象(判明する場合)/ 期限・施行日(あれば)/ 出典 URL」を項目ごとに含む。見出し・要点・出典 URL は必須。対象と期限は原文から読み取れない場合に空でよい(推測で埋めさせない。NFR-02) | Must |
| FR-07 | まとめは 3〜7 項目に絞り込み、重要度順に並べる。7 件超は「その他 N 件」として件数のみ示す | Must |
| FR-08 | すべての出典 URL は配信前に到達確認(2xx または 3xx)を行う。官公庁サイトはリダイレクトが多いため 3xx も到達とみなす。検証失敗の項目は配信から除外し、運用者へ通知する | Must |
| FR-09 | 生成テキストは LINE の 1 メッセージ上限(5,000 文字)以内、目標 1,500 文字以内とする | Must |
| FR-10 | 07:30 JST に各チャネルの LINE 公式アカウントへブロードキャスト(全友だち)配信する | Must |
| FR-11 | 該当情報が 0 件の日も「本日の新着はありません」を必ず配信する(初期値: 配信する)。受信者が「配信が届かない = システム障害」と判別できるようにするため。スキップ運用はチャネル設定で切替可能 | Must |
| FR-11a | 「新着なし」配信には巡回したソース数と巡回時刻を添え、正常に監視したことを示す(例: `本日 06:00 時点で 38 ソースを確認しました`) | Should |
| FR-12 | 配信は冪等とし、同一日・同一チャネルの二重配信を防ぐ | Must |
| FR-13 | 運用者は Slack または Discord の通知先で「失敗 / 除外された項目」を受け取れる | Should |
| FR-14 | 運用者は手動で「収集」「要約」「配信」を個別に再実行できる | Should |
| FR-15 | 「承認モード」を有効にすると、配信前に運用者へプレビューを送り、承認後に配信する | Could |
| FR-16 | 配信履歴と生成に使った元記事・プロンプト・モデル応答を 90 日保持し、監査可能とする | Must |
| FR-18 | 自治体情報には地域名を明記し、国の情報と区別できるようにする | Must |
| FR-17 | 緊急性の高い情報(重要度=高 かつ 種別=法改正/報酬改定)は、翌朝を待たず当日 18:00 巡回後に「速報」として配信できる(設定で ON/OFF、初期値 OFF) | Could |

## 7. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 可用性 | 日次配信の成功率 99.5% 以上。単一ジョブ失敗時は自動リトライ(最大 3 回、指数バックオフ) |
| NFR-02 | 正確性 | 要約は元記事に含まれる事実のみを用いる。日付・金額・数値は原文から抽出し、推測しない。AI 出力は構造化出力(JSON Schema)で受け取り、必須項目の欠落をプログラムで検出する |
| NFR-03 | セキュリティ | LINE チャネルアクセストークン・Anthropic API キー・通知 Webhook URL は Secret Manager で管理し、コード・ログに出力しない。最小権限のサービスアカウントで実行 |
| NFR-04 | コスト | クラウド基盤 + AI API の月額ランニングコスト目標 3,000 円以下。LINE 公式アカウントのプラン料金(2 アカウント分)は別枠で予算化する。AI 呼び出しは 1 日あたり判定バッチ + チャネル数分の要約に限定 |
| NFR-05 | 保守性 | 情報源追加は YAML 1 ブロックの追記で完了。全ジョブは単一コマンドでローカル再現可能 |
| NFR-06 | 観測性 | 各ジョブの開始・終了・処理件数・失敗理由を構造化ログに記録。失敗は 10 分以内に通知 |
| NFR-07 | 礼節・負荷 | 各サイトの robots.txt を尊重し、同一ホストへのアクセス間隔を 2 秒以上空ける。User-Agent に連絡先を明記 |
| NFR-08 | タイムゾーン | すべてのスケジュールは JST 基準。内部保存は UTC |
| NFR-09 | 拡張性 | チャネルは 3 つ目以降も YAML 追記のみで追加可能 |

## 8. 技術的実現可能性の評価

| 論点 | 評価 | 根拠 |
|---|---|---|
| LINE 公式アカウントへの自動配信 | **可能** | LINE Messaging API のブロードキャスト機能で全友だちへ送信可能。チャネルごとにアクセストークンを取得すれば 2 アカウントを 1 システムから配信できる |
| 配信コスト | **要契約(低額)** | 友だち数は各アカウント最大 20 名程度。1 日 1 通 × 20 名 × 31 日 ≒ 620 通/月/アカウント。無料のコミュニケーションプラン(200 通/月)を超えるため、各アカウントでライトプラン(5,000 通/月)の契約が必要。※ 通数上限と料金は LINE 側の改定があるため、契約時に最新の料金表で再確認する |
| 省庁サイトの監視 | **可能(要保守)** | RSS を提供するサイトは安定。HTML 差分監視はサイト改修で壊れる可能性があるため、取得失敗を検知して通知する仕組みを必須とする |
| AI による要約と出典付与 | **可能** | 元記事の URL とテキストを AI に渡し、構造化出力で「出典 URL は入力に含まれるものだけを使う」制約を課す。さらにプログラム側で URL 実在性を検証する二重ガードで幻覚を防ぐ |
| 情報過多の抑制 | **可能** | 関連度スコアによる事前フィルタ + AI 側で件数上限を指定 + 文字数の機械的検証 |

**結論: 技術的に実現可能。** リスクは「監視対象サイトの構造変更」と「LINE 無料通数」の 2 点であり、いずれも運用設計で吸収できる。

## 9. 制約・前提

- LINE 公式アカウントは 2 つとも事業者側で開設済み、または本プロジェクト開始時に開設する。Messaging API を有効化し、チャネルアクセストークン(長期)を発行できること。
- 実行基盤は Google Cloud(Cloud Run Jobs + Cloud Scheduler + Firestore + Secret Manager)を第一候補とする。AWS 等に変更する場合も設計は変わらない(詳細設計書 §2 参照)。
- 要約 AI は Anthropic Claude(モデル `claude-opus-5`)を使用する。
- 配信メッセージは日本語。
- 配信は 1 日 1 回(毎朝 07:30 JST)のみ。速報配信(FR-17)は将来拡張とし、初期リリースでは実装しない。
- 受信者は各アカウント最大 20 名程度(社内チームメンバー)。

## 10. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| サイト構造変更で取得失敗 | 見落とし | 取得失敗の即時通知、ソース単位のヘルスチェック、RSS 優先 |
| AI が不正確な要約を生成 | 誤情報の拡散 | 構造化出力 + 出典 URL 限定 + URL 実在検証 + 免責文言 + 抜き取り監査 |
| 自治体ページの構造が多様で取得が壊れやすい | 自治体情報の見落とし | 自治体ソースは都府県庁・政令市から段階導入し、ソース単位のヘルスチェックで壊れたページを翌日までに検知 |
| 情報量が多すぎ/少なすぎ | 読まれない | 関連度閾値と件数上限をチャネルごとに調整可能にする。週次で件数レポート |
| LINE API 障害 | 配信欠落 | リトライ + 失敗通知 + 手動再配信コマンド |
| API キー漏洩 | 不正利用 | Secret Manager、最小権限、ローテーション手順の文書化 |

## 11. 配信メッセージ仕様(例)

```
【本日の制度・法改正まとめ】9/11(金)
就労支援、放課後デイ情報局

■1. 【重要】令和8年度 障害福祉サービス等報酬改定 Q&A(第3報)公表
　放課後等デイサービスの「専門的支援実施加算」の算定要件が明確化。
　対象: 放課後等デイ / 児童発達支援
　出典: https://www.mhlw.go.jp/...

■2. 就労選択支援 実施要綱の一部改正について(通知)
　アセスメント様式の変更。10/1 適用。
　対象: 就労移行 / 就労継続B型
　出典: https://www.mhlw.go.jp/...

■3. パブコメ: 児童福祉法施行規則の一部改正(案)
　意見募集は 9/30 まで。
　出典: https://public-comment.e-gov.go.jp/...

その他の新着 2 件は重要度が低いため割愛しました。

※本まとめはAIが公的情報・報道を要約したものです。報道は速報であり、実際の手続きは必ず出典元の公的情報をご確認ください。
```

新着が 0 件の日の配信例:

```
【本日の制度・法改正まとめ】9/12(土)
就労支援、放課後デイ情報局

本日の新着はありません。
(本日 06:00 時点で 38 ソースを確認しました)

※この配信が届かない日はシステム障害の可能性があります。管理者へご連絡ください。
```

## 12. 用語

| 用語 | 定義 |
|---|---|
| ソース | 監視対象の URL または RSS フィード 1 件 |
| アイテム | ソースから検知した個別の記事・通知・ページ更新 1 件 |
| ダイジェスト | 1 チャネル・1 日分の AI 生成まとめ |
| チャネル | 配信先の LINE 公式アカウントと、それに紐づく話題領域 |
